# 生生之境 V1：規劃設計建議（GDD v3.1 審查）

> 本文件是對 `docs/GDD_v3.1.md` 的審查與實作規劃建議。**GDD 仍是唯一有效規格**；
> 本文件中標「需拍板」的項目在開發者確認前，實作一律採「暫定做法」並以 ADR 記錄。

## 1. 總評

GDD v3.1 的範圍收斂得很好：單聚落、5 種商品、提案驅動、關閉即暫停、headless 先行。
最大的風險不在系統數量，而在 **經濟閉環的數值是否真的能自我調節**，以及 **15 分鐘切片是否好玩**。
因此建議嚴格照 A0 → A1 → A2 的「無畫面先行」路線，A3 才投入地圖與美術。

## 2. 規格內的矛盾與缺口（需拍板）

## 3. 數值推算（供校準參考）

**糧食季節曲線**（3 田 × 3 人、每次收成約 2,892，日耗 24）：

| 時點 | 存糧（未計損耗） |
|------|------------------|
| 開局 春 60 日 | 1,020 |
| 春末收成前 | 300 |
| 春末收成後 | 3,192 |
| 夏末收成後 | 3,924 |
| 秋末收成後 | 4,656 |
| 冬末 | 2,496 |
| **第二年春末收成前** | **336** |

再扣每月 1% 損耗（年約 −360）與年產略低於需求（−324），**第二年春荒幾乎必然缺糧**。
這符合「刻意偏緊」的設計，但代表 A2 一定要先有救濟與節點採購，否則 headless 3 年測試無法通過。
建議把「第二年春季缺口 ≈ 300–700」寫進 A2 的預期值，作為校準基準。

**勞力**：14 名工作者 × 300 工作日 = 4,200 人日，與 7.8 一致；工具 56 件 ≈ 84 人日、家具 30 件 ≈ 60 人日、燃料 540 木材 ≈ 90 人日，數字互相吻合。

## 4. 技術建議

1. **套件管理用 pnpm workspaces**，TypeScript strict、Vitest、ESLint flat config。
2. **決定性基礎先做好再寫任何玩法**：
   - PRNG：sfc32（只用 `Math.imul` 與位元運算，跨引擎一致），狀態存進世界。
   - 定點數工具：`fxMul`、`fxDiv` 一律 floor 截斷，集中在一個模組。
   - 狀態 hash：對「鍵排序後的正規化 JSON」做 64 位元 FNV-1a 系雜湊（雙 32 位元實作）。
   - ESLint 在 `packages/sim` 禁用 `Math.random/exp/pow/sin/cos/log...`、`Date`、`performance`、`**` 運算子、DOM 全域與 `phaser` import。
3. **Phaser 延到 A3 才加入**：A1 的「簡易除錯畫面」用 DOM 就夠，少一個大依賴與一層除錯成本。
4. **SoA（TypedArray）延到效能需要時**：24 人規模下 AoS 純物件更好寫、好序列化、好比對。保留 SoA 作為 B 階段或 200–500 人壓測時的優化（需 ADR，因與 11.2 有偏差）。
5. **世界狀態保持「純 JSON 可序列化」**：不放 Map／Set／class 實例，存檔與 hash 才能保證一致。
6. **速度只在 Worker 排程層**：Worker 依速度決定每秒呼叫幾次 `step()`，世界本身只有「日」的概念。

## 5. 玩法設計建議

1. **提案是主動詞，要有足夠密度**：每季 3 件上限下，15 分鐘切片內約 3–6 件提案。建議 A3 前先在 headless 統計「每季觸發的提案數」，避免空窗。
2. **第一個春荒就是最好的教學**：開局 30 日後的春收很順，但第二年春荒是第一個真危機；建議在秋末加入「存糧撐不到春收」的預警提案（2.3 已有觸發條件），讓玩家第一次面對 2.6 的四選一。
3. **偏袒判定的最低支出門檻**：小村第一條路很可能剛好經過玩家家族的田，建議門檻設為「累計公共支出 ≥ 年度公共收入的 50%」才判定。
4. **支持度可讀性**：主畫面只顯示數字與箭頭，點開後顯示前 3 個因子（例如「農戶：取消補助 −8」），對應 2.4 的因果回顧。
